# 115 网盘自动化集成方案

面向 nfo-editor 的「磁力离线 → 自动归档 → 元数据上传」全链路方案

版本：v1（讨论稿）
日期：2026-09-04

---

## 一、目标与范围

### 1.1 最终产品形态

在 nfo-editor（单文件 H5，手机端为主）中，通过两次点击完成影片入库：

- **点「磁力」** → 自动完成：提交 115 云端离线下载 → 归档 → 只留最大视频 → 改名 → 结束
- **点「下载元数据」** → 自动完成：把 NFO + 图片上传到对应影片文件夹（文件夹不存在则自动创建）

### 1.2 已确认的设计前提

| 项 | 结论 |
|---|---|
| 登录方式 | **手机端配置 cookie**，存 IndexedDB，不存云端 |
| 下载方式 | **115 云端离线下载**，非本地 BT |
| 场景范围 | **只处理「秒下」**（提交后 5 秒内完成） |
| 轮询策略 | 提交后**等 5 秒，只查一次**；成功继续，失败返回失败 |
| 归档规则 | 新建文件夹（名 = 标题）→ 移入**体积最大的视频** → 视频改名为**番号** |
| 元数据 | NFO + 图片上传到「标题」同名文件夹，不存在则创建 |
| 设备约束 | 电脑不常开，需云端（serverless）能力 |

### 1.3 不在本方案范围

- 非秒下场景的长时轮询（本方案直接判失败）
- 115 网盘以外的其他网盘
- nfo-editor 已有功能（TMDB 刮削、海报生成等）的重构

---

## 二、核心结论摘要

1. **技术上 100% 可落地**。每一环节 115 都有现成接口，且已有成熟开源库封装。
2. **纯前端做不到**。115 接口存在 CORS 跨域限制，且需要登录态与加密签名，nfo-editor 单文件 HTML 无法直连。**必须有一个后端中转**。
3. **cookie 不需要存云端**。cookie 只存在手机本地（IndexedDB），中转服务只做「无状态转发」，用完即弃、不落盘 —— 这是本方案安全设计的核心。
4. **唯一需要解决的工程问题是「后端用什么语言跑在 Vercel」**，因为成熟的 115 客户端库是 Go / Python，而 Vercel 的舒适区是 Node。方案给出三条候选路线（见第六章）。

## 三、架构设计

### 3.1 总体架构

```
┌──────────────────────────────────────┐
│  nfo-editor（手机浏览器 / PWA）        │
│  · 点「磁力」/「下载元数据」            │
│  · cookie 存 IndexedDB（本地，不上云） │
│  · 负责「编排」：多次调用 + 5 秒等待   │
└──────────────┬───────────────────────┘
               │ HTTPS，每次请求临时携带 cookie
               ▼
┌──────────────────────────────────────┐
│  Vercel 中转服务（无状态）             │
│  · 不存储 cookie，不落盘，不记日志     │
│  · 每个接口只做一件事（短请求）        │
│  · 建议复用 nfo-magnet-proxy-vercel   │
└──────────────┬───────────────────────┘
               │ 115 API（带 cookie + 签名）
               ▼
┌──────────────────────────────────────┐
│  115 网盘                             │
│  离线下载 / 文件管理 / 上传            │
└──────────────────────────────────────┘
```

### 3.2 为什么「编排」放在前端

关键设计决策：**5 秒等待不放进后端，而是前端 `setTimeout`**。

原因：Vercel Hobby 计划的单次函数执行时长有限（约 10 秒量级），若把「提交 → 睡 5 秒 → 轮询 → 归档」压进一个请求，极易超时。拆成多个短请求由前端编排，每个请求都在 1–2 秒内返回，稳定且可重试。

```
前端编排（每个请求都很短）：
  POST /115/offline/add   ── 提交磁力
  (等待 5 秒)
  POST /115/offline/list  ── 查一次状态
  POST /115/dir/list      ── 列 INBOX 找最大视频
  POST /115/dir/mkdir     ── 建「标题」文件夹
  POST /115/file/move     ── 移入最大视频
  POST /115/file/rename   ── 改名为「番号」
  POST /115/file/delete   ── 清理其余残留
```

## 四、详细流程

### 4.1 第一部分：点磁力 → 自动归档

#### 前置约定

- `INBOX`：115 中的暂存目录，例如 `/_inbox`（可配置）。离线下载统一落到这里，避免污染正式影片库。
- `LIB`：正式影片库根目录，例如 `/影片库`（可配置）。
- 前端需持有的三个字段：**磁力链接**、**标题**（文件夹名）、**番号**（视频名）。

#### 流程步骤

| 步骤 | 动作 | 说明 |
|---|---|---|
| 1 | 提交离线任务 | 把磁力提交给 115，指定落到 `INBOX` |
| 2 | 等待 5 秒 | 前端 `setTimeout(5000)` |
| 3 | 查询任务状态（只查一次） | 已完成 → 继续；下载中/失败 → 返回失败，结束 |
| 4 | 列出 INBOX 新增内容 | 若出现唯一子文件夹（115 常为种子名建一层），则进入该子文件夹 |
| 5 | 筛选视频文件 | 按扩展名白名单过滤；排除文件名含 sample / 预览 / trailer 的样本片 |
| 6 | 找体积最大者 | 按 size 降序取第一 |
| 7 | 新建「标题」文件夹 | 在 `LIB` 下 `mkdir {标题}`；若已存在则复用 |
| 8 | 移动最大视频 | 移入 `{LIB}/{标题}/` |
| 9 | 重命名为「番号」 | 改为 `{番号}.{原扩展名}`，保留原扩展名 |
| 10 | 清理残留 | 删除 INBOX 中该次任务的其余文件与子文件夹（先进回收站） |
| 11 | 返回成功 | 结束 |

#### 关于第 4 步的子文件夹问题

115 的离线下载在处理磁力时，**常见行为是在目标目录下再建一层以种子名命名的文件夹**。这会导致期望的 `/标题/番号.mp4` 变成 `/标题/{种子名}/番号.mp4`。

处理方式：列目录后判断——若目标下只有**一个**子文件夹且没有视频文件，则下沉一层再找最大视频。这个行为**需要实测确认**（见第八章待验证项）。

#### 关于第 10 步的删除安全

- 115 的删除默认进**回收站**，可恢复。建议保持默认，稳妥。
- 清理范围严格限定在 INBOX 内本次任务产生的条目，**绝不递归清理 LIB**。

---

### 4.2 第二部分：点「下载元数据」→ 上传 NFO 与图片

| 步骤 | 动作 | 说明 |
|---|---|---|
| 1 | 查找「标题」文件夹 | 在 `LIB` 下按名称精确匹配 |
| 2 | 不存在则创建 | `mkdir {标题}` |
| 3 | 上传 NFO | 命名为 `{番号}.nfo` |
| 4 | 上传图片 | poster → `{番号}-poster.jpg`，fanart → `{番号}-fanart.jpg` |
| 5 | 返回成功 | 结束 |

#### 命名说明

- NFO 与视频文件同名（`{番号}.nfo` ↔ `{番号}.mp4`），Kodi / Plex 才能正确关联刮削。
- 图片用 `-poster` / `-fanart` 后缀，是 Kodi 的标准命名约定。
- 若使用 `movie.nfo` / `poster.jpg` 通用名也能被识别，但多影片批量时易冲突，**推荐番号命名**。

#### 命名规则待确认

你指定的规则是「文件夹 = 标题，视频 = 番号」。需留意：**部分 Kodi 刮削器更依赖「文件夹名包含番号」**来识别影片。若 NFO 里已写入正确的 `<id>` 与 `<title>`，绝大多数刮削器能正常工作，但建议把命名模板做成**可配置**：

```
文件夹名模板：{番号} / {标题} / {番号} {标题}   ← 默认 {标题}
视频名模板：  {番号} / {标题}                 ← 默认 {番号}
```

## 六、关键技术决策：Vercel 运行时选型

这是本方案**唯一需要试错的工程点**。问题在于：成熟的 115 客户端库是 Go / Python，而 Vercel 的原生舒适区是 Node。

### 三条候选路线

| 路线 | 做法 | 优势 | 风险 |
|---|---|---|---|
| **A. Python + p115client** ⭐推荐 | Vercel Python 运行时，`api/115.py` 直接 import p115client | 库最成熟（离线/上传/加密全实现），零重复造轮子；Vercel 原生支持 Python | 依赖体积与冷启动需实测 |
| B. Go + 115driver | Vercel Go 运行时，`api/115.go` import `pkg/driver` | 同样零重复造轮子，性能最好 | Vercel 的 Go 支持不如 Node/Python 成熟，构建体积与冷启动是风险 |
| C. Node + 自行实现 | 在现有 `api/index.js` 里手写 115 各端点 | 与你现有代理一致，无需新运行时 | 需自行实现 115 的请求签名（ECDH/AES/RSA）与上传流程，**工作量最大** |

### 推荐与执行顺序

**先试 A（Python + p115client），不成再试 B，C 作为兜底。**

理由：p115client 是 Python 生态里 115 客户端的事实标准（也是 `115-MCP-Server` 的底座），「秒传 SHA1 + OSS 分片上传」「离线任务」「文件增删改移」全部实现完毕，直接用能省掉大量底层工作。Vercel 对 Python 有原生支持，接入成本低。

> 补充：三个路由里，**上传小文件（NFO / JPG）** 是唯一有实现难度的部分（涉及 SHA1 秒传 + OSS 分片）。其余接口都是简单的带 cookie HTTP 调用。因此即使走路线 C，也只有上传这一步硬。

## 七、安全设计

### 7.1 核心原则

> **cookie 永久只存在你的手机里，中转服务只在单次请求的内存中经手一次，不落盘、不存储、不记录日志。**

### 7.2 与「云端存 cookie」方案的对比

| 方案 | cookie 位置 | 泄漏风险 | 评价 |
|---|---|---|---|
| 云端保存（Vercel 环境变量） | 云端长期驻留 | 高 | ❌ 钥匙放别人家，不推荐 |
| **手机本地 + 无状态转发** ⭐ | 仅手机 IndexedDB | 低 | ✅ 本方案采用 |
| 手机本地 + 本地服务 | 仅本地 | 最低 | 但电脑需常开，不符合约束 |

### 7.3 必须遵守的红线

| 编号 | 规则 |
|---|---|
| S1 | **绝不**把 cookie 硬编码进任何会 push 到 GitHub 的文件（你的 nfo 仓库是公开的） |
| S2 | **绝不**把 cookie 存进 Vercel 环境变量（那是云端长期驻留） |
| S3 | `.env` 必须进 `.gitignore` |
| S4 | **绝不**在前端代码里 `console.log` cookie，或写进 `NEXT_PUBLIC_*` 类变量 |
| S5 | 中转服务**不记录请求日志**，或日志脱敏后只保留非敏感字段 |
| S6 | 中转服务**不做任何持久化**，纯内存转发 |

### 7.4 建议的加固措施

- **给中转服务加一个共享密钥**（自定义 header，如 `X-Proxy-Token`）：即使代理 URL 泄露，别人没有密钥也无法白嫖你的代理去刷 115。
- **开启 Vercel Deployment Protection**：限制部署站点的匿名访问。
- **cookie 定期重登**：115 cookie 在改密码 / 异地风控 / 长期不用后会失效，失效后需在手机端重新配置一次。这是正常的预期行为，不是 bug。
- **删除默认进回收站**：误删可恢复。

### 7.5 残留风险（需你知情）

中转服务在**转发请求的瞬间**，cookie 会经过其内存。理论上若 Vercel 平台在该瞬间被攻破，存在极小概率泄漏。这是「要云端能力」就必须接受的代价 —— 但它比「云端长期存储 cookie」安全一个量级，因为攻击者需要精确命中一个毫秒级的时间窗口，而不是随时可读。
