## 二、登录入口与「115 配置页」UI 设计

| 端 | 入口 | 参照模式 |
|---|---|---|

### 2.2 「115 配置页」布局（两端统一语义）

```
┌─────────────────────────────────┐
│  115 网盘配置                      │  ← 标题
│ ┌───────────────────────────────┐ │
│ │        [ 二维码图片 ]           │ │  ← 扫码登录区（主视觉）
│ │   请使用 115 App 扫码登录        │ │
│ │   状态：已扫码，请在 App 确认…   │ │  ← 状态文案（见 2.4）
│ └───────────────────────────────┘ │
│ ┌───────────────────────────────┐ │
│ │ [ cookie 输入框（自动填充/可编辑）]│ │  ← 扫码成功自动填；也支持手动粘贴
│ └───────────────────────────────┘ │
│   [ 保存配置 ]  [ 清除 ]           │  ← 胶囊按钮（iOS）/ panel 按钮（PC）

└─────────────────────────────────┘
```

### 2.3 两端样式对齐

- **iOS**：底部弹出 sheet（参照 `openApiKeySheet`），二维码区居中、尺寸约 200×200，状态文案在二维码下方，cookie 输入框为全宽输入框，底部胶囊按钮（保存 / 清除）。
- **PC**：右侧 panel（参照 `openSettingsMini`），布局同上，按钮为 panel 内标准按钮。
- 扫码中/轮询中：二维码上方显示转圈；过期显示「二维码失效，点击刷新」。

### 2.4 状态机（扫码登录）

```
生成中 → 等待扫码（请使用115 App扫码）
       → 已扫码，请在 App 确认…
       → 登录成功（自动填充 cookie，提示保存）
       → 失败/超时（二维码失效，点击刷新重新生成）
```

## 三、扫码登录流程（核心新增）

### 3.1 时序

```
前端(nfo-editor)          后端中转(/api/115/*)           115 网盘
     │                          │                          │
  1. GET /api/115/qrcode ─────►│                          │
     │                          ├─ 调 115 拿 {qrcodeContent,│
     │                          │   uid, sign} ──────────►│
     │◄──────── {qrcode,uid,sign}│◄───────────────────────│
  2. 用 qrcode 库渲染图片         │                          │
  3. 用户用 115 App 扫码并确认 ───────────────────────────►│
  4. 每 1.5s 轮询                │                          │
     GET /api/115/qrcode/status?uid&sign ─►│                │
     │                          ├─ 查 115 状态 ───────────►│
     │                          ├─ 已确认→兑换完整 cookie ─►│
     │◄──────── {status, cookie}│◄───────────────────────│
  5. 前端填充 cookie 输入框       │                          │
     + 存 IndexedDB             │                          │
```

### 3.2 关键实现说明

- **二维码内容**：由后端从 115 获取（115 扫码登录接口返回的字符串 / URL），前端用轻量 `qrcode` 库（约 20KB）渲染成图片。具体格式需 P0 实测（见第六章）。
- **轮询策略**：前端 `setInterval` 每 1.5s 查一次状态；**二维码有效期约 120s**，超时提示失效、用户点刷新重新走 3.1 第 1 步。
- **cookie 兑换**：115 扫码「已确认」后，后端需用 `uid + sign` 二次调 115 兑换完整登录态（含 `UID/CID/SEID/KID`），这一步是 P0 必须验证的关键（见第六章风险点）。
- **自动填充**：登录成功后后端返回的 cookie 字段直接写入输入框 `value`，无需用户手动复制；用户点「保存配置」才落 IndexedDB。
- **手动兜底**：输入框始终可手动粘贴 cookie（v1 的 10.4 方式），扫码失败/无 App 时仍可用。

## 四、后端中转端点（v1 八端点 + 扫码三端点）

复用 `halfleave/nfo-magnet-proxy-vercel`，新增以下端点（其余 8 个业务端点不变）：

| 端点 | 方法 | 入参 | 出参 |
|---|---|---|---|
| 扫码登录-获取二维码 | `GET /api/115/qrcode` | 代理密钥 | `{ qrcode: <字符串/URL>, uid, sign, expire }` |
| 扫码登录-查状态 | `GET /api/115/qrcode/status` | `uid`, `sign`, 代理密钥 | `{ status: 'waiting'\|'scanned'\|'confirmed'\|'expired', cookie?: {UID,CID,SEID,KID} }` |
| 连通性自检 | `GET /api/115/ping` | cookie, 代理密钥 | `{ ok: true/false }` |

- 扫码端点**无状态**：`uid/sign` 由前端在轮询时回传，后端不存储。
- 安全：与 v1 一致，所有端点加 `X-Proxy-Token` 共享密钥校验；中转不落盘、不记日志。
- Vercel 运行时选型：沿用 v1 第六章结论——**先试 A（Python + p115client）**（其已实现 115 扫码登录与 cookie 兑换），不成再 B（Go + 115driver），C（Node 手搓）兜底。

## 五、安全红线（重申，同 v1 第七章）

1. cookie **永久只存手机 IndexedDB**，中转仅在单次请求内存经手一次，不落盘、不记日志。
2. **绝不**把 cookie 硬编码进任何 push 到 GitHub 的文件（nfo 仓库公开）。
3. **绝不**把 cookie 存 Vercel 环境变量。
4. 中转服务加 `X-Proxy-Token` 共享密钥，防代理被滥用。
5. 删除默认进回收站（误删可恢复）。

## 六、P0 能力验证（Spike，最高优先级）

在写任何业务代码前，必须先用真实 115 账号验证以下项（建议接 115 MCP / 115driver 先跑通）：

| # | 验证项 | 为什么关键 |
|---|---|---|
| **P0-1** | **115 扫码登录 API 是否可用** | 确认能拿到二维码内容（qrcode 字符串/URL）+ `uid/sign` |
| **P0-2** | **扫码「已确认」后能否兑换完整 cookie（UID/CID/SEID/KID）** | ⚠️ 最关键环节：扫码登录态 ≠ 直接可用 cookie，需确认兑换链路 |
| **P0-3** | 兑换出的 cookie 能否直接调离线下载/文件管理 API | 确认 web 登录 cookie 与 API 用 cookie 是同一套 |
| P0-4 | v1 第八章原 9 项（状态枚举/秒下成功率/子文件夹/分页/运行时/上传端点/cookie 有效期/字段来源/会员配额） | 业务落地前提 |
| P0-5 | Vercel Python 运行时能否跑 p115client 的扫码 + 业务接口 | 决定路线 A 是否可行 |

**P0 产出**：上述项全部有答案 + 确定运行时选型 + 确认扫码登录端到端可行，再进入 P1/P2 开发。
